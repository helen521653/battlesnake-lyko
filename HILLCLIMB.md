# Hill-climbing змейки с помощью LLM-агента

Задача поставлена в духе статьи
[«LLMs are fantastic at hill-climbing»](https://www.noahrousell.com/blog/llms-are-fantastic-at-hillclimbing-will/).
LLM хорошо улучшают решение, если есть **быстрый, плотный и труднообманываемый сигнал проверки**:
модель предлагает много несложных идей, каждая проверяется, сохраняются только улучшения.
Главный риск — reward hacking, то есть подгонка под метрику вместо настоящего улучшения.
Поэтому основная работа здесь — в стенде, который такой подгонке сопротивляется.

## Что улучшается

Улучшается весь код змейки в папке [snake/](snake/): поиск, оценка, скорость, веса.
Меняется только он. Интерфейс фиксирован: `snake.api.move(req) -> ({"move": ...}, info)`,
и ответ должен приходить за `game.timeout − LATENCY_MS` мс.

## Сигнал: `python3 bench.py run --idea "..."`

| Проверка | Зачем |
|---|---|
| `tests/` проходят | правила и базовое поведение не сломаны |
| **timing**: на одном ядре в боевых настройках (timeout 500) максимальный ход < 450 мс | требование задания, и экономия времени здесь не выгодна |
| **80 игр против текущего чемпиона**, парами: одна раздача играется дважды со сменой сторон | главный сигнал. Парность снижает дисперсию |
| принятие при **LOS ≥ 0.95** (likelihood of superiority) и счёте > 50% | улучшение статистически значимо, а не шум |
| игры против 2 предыдущих чемпионов, счёт ≥ 45% | защита от циклов «камень-ножницы-бумага» |
| игры против пула ботов других стилей ([harness/opponents.py](harness/opponents.py)) | защита от переобучения на игру против себя |
| ни одной ошибки и грубого таймаута в партиях | надёжность |

Почему стенд трудно обмануть:
- игры судит **независимый рефери** [harness/referee.py](harness/referee.py), который не использует код змейки.
  Ошибка или подгонка в `snake/rules.py` не меняет результат, а только ухудшает игру змейки;
- рефери сам замеряет время. Если змейка не уложилась, засчитывается её прошлый ход, как в настоящем движке.
  Поэтому выиграть за счёт лишнего времени на раздумья нельзя;
- сиды раздач новые при каждом запуске (записываются в журнал для воспроизводимости).
  Подогнать змейку под фиксированный набор позиций не получится;
- стенд (`bench.py`, `harness/`, `champions/`, `tests/` в части уже существующих тестов)
  в ходе экспериментов **не меняется**.

## Цикл одной итерации

1. Выбрать одну идею (из бэклога в [experiments/JOURNAL.md](experiments/JOURNAL.md) или новую).
2. Реализовать её в `snake/`, по возможности маленьким изменением.
3. По желанию: `python3 bench.py run --quick --idea "..."` (примерно минута) — быстрая прикидка, отсеять явные провалы.
4. `python3 bench.py run --idea "..."` (примерно 5 минут) — вердикт **ACCEPT / REJECT**.
5. **ACCEPT** → `python3 bench.py promote --idea "..."`, затем `git commit` (код, чемпион и журнал).
   **REJECT** → `git checkout -- snake/`, в журнал — запись о том, что не сработало и почему.
6. Записать итог в `experiments/JOURNAL.md`. Машиночитаемый журнал всех прогонов —
   `experiments/log.jsonl`, его пишет сам стенд.

Чемпион повышается только через ACCEPT, поэтому каждая следующая версия статистически
сильнее предыдущей. Это и есть подъём на холм.

## Важно: стенд ≠ арена

Стенд измеряет силу относительно предыдущих версий. Настоящая проверка — рейтинг на
arena.battlesnake.com. Принятые версии стоит деплоить на сервер и следить за лидербордом:
если рейтинг падает, значит, стенд что-то не отражает, и его нужно обсудить с человеком,
а не подгонять.
